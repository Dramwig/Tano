# 本地工作区打开性能

2026-11-05 针对 `codex-learn` 工作区切换等待数十秒的问题，使用独立目录副本和 SQLite 一致性备份测量，未用性能探针修改原工作区或原索引。

## 测量范围

原目录有 4,338 个文件、884 个目录，约 38 MB；其中 471 篇 Markdown，共约 3.1 MB。按存储适配器的隐藏目录规则过滤后，扫描返回 5,130 个文件和目录条目。

Windows 本机、Rust debug 构建的测量结果：

| 环节 | 结果 |
| --- | --- |
| 只枚举目录与文件元数据 | 约 102 ms |
| 缓存有效的完整存储扫描 | 约 440–512 ms |
| 逐篇执行身份校验并读取 471 篇 Markdown，修改前 | 13,016 ms |
| 相同副本、相同读取操作，复用身份校验后 | 146 ms |

首次副本扫描测到过 13.4 s，后续重新建立缓存的样本为 1.7–2.4 s。文件缓存状态、复制后的原生文件身份和初次读盘会影响这些数值，不能把它们当成同条件的优化前后对比。

上表记录独立组件计时。随后在当前桌面开发版中完成三轮实际菜单往返切换，结果见下一节。

## 桌面切换实测

2026-11-05，在 Windows 桌面 debug 开发版中，通过工作区菜单在 `markdown-test-workspace` 与 `codex-learn` 之间往返切换三轮。使用当前已有缓存，恢复 `build-from-zero/README.md`。每次测量期间均关闭开发者工具。

| 切回 codex-learn | 文件列表就绪 | 正文就绪 | 切换完成 |
| --- | --- | --- | --- |
| 第一轮 | 774 ms | 1,047 ms | 1,190 ms |
| 第二轮 | 765 ms | 1,025 ms | 1,156 ms |
| 第三轮 | 738 ms | 1,002 ms | 1,132 ms |

三轮平均切换耗时为 1,159 ms，均返回 5,130 个文件和目录条目，恢复当前文档，工作区错误状态为空。每轮切换后均通过桌面截图确认文件列表和正文显示正常。

计时从工作区进入加载状态开始，通过 `requestAnimationFrame` 检测文件列表和编辑器正文的 DOM 就绪状态，并在加载状态结束后的下一帧记录完成时间。这些数值包含工作区切换、文件列表准备和当前文档恢复的耗时。首次建立索引和冷启动需要单独测量。

三轮中最长的主线程长任务为 152 ms，切换期间仍有短暂阻塞。临时计时订阅和性能观察器已移除，桌面停留在 `codex-learn` 的原文档。

## 已消除的重复工作

- 机器人收件箱定时检查曾在没有机器人连接时也扫描工作区，并逐篇读取 Markdown。现在没有本地连接和任务时，不进行文件扫描和正文读取。
- 对有机器人连接的工作区，使用扫描返回的内容 hash 识别稳定版本；内容和连接配置不变时不重复读取、解析或协调提及。外部修改、删除和新增连接仍会重新处理。缺少内容 hash 的适配器保持读取回退。
- 桌面机器人检查复用已有文件监听和后备轮询发布的文件列表，不再每两秒另起一次完整扫描、与打开和保存操作竞争工作区锁。
- 切换开始后，不再继续安排旧工作区的下一篇文档读取；已经开始的操作安全结束后交接。
- 每个本地命令此前都重新读取、解析和验证整份身份清单。现在只缓存“这个文件版本已验证”的结果，最多保留八个文件。标识包含文件原生身份和 change time；修改时间和长度相同也不能直接命中。

身份清单的写入、比较和冲突保护仍直接读取真实文件。配置身份仍在每次命令中检查；文件状态不可靠或 Windows 存在未关闭的写句柄时，退回完整验证。缓存只在内存中，不进入用户工作区。

## 回归检查

- 471 篇文档、无机器人连接时，跨多个检查周期没有正文读取或工作区扫描。
- 未变文档只读取一次；同大小修改、提及移除、文件删除、新增连接和无 hash 适配器都继续协调任务。
- 切换中停止后续读取，取消切换后可继续处理。
- 身份清单同大小修改并恢复 mtime、原子替换、删除、工作区身份变化和打开中的写句柄均不能绕过验证。

身份校验缓存不会跳过文件保存时的内容 hash 比较，也不会改变多人协作中的文档身份。

本次本地检查：机器人控制器、提及、任务队列、身份创建和工作区监听共 26 项前端测试通过；原生身份相关筛选 35 项通过，存储相关筛选 56 项通过、1 项跨卷测试按默认设置忽略（两个筛选存在重叠）。客户端类型检查、Rust 格式化和文档链接检查通过。

Tano-cloud 的 `npm run core:check` 未通过：当前桌面开发配置使用本地 Core，`Cargo.lock` 没有发布包的 registry 来源和 checksum。这是发布依赖一致性检查的限制，不计作已通过，也未为本次本地优化改动发布依赖。
